```text
           │                            │

```

## 2\. 关键设计决策

-   **调度引擎**：推荐 **Asynq**，理由：
    
    -   基于 Redis，天然支持分布式、延时/定时任务、重试、优先级。
        
    -   与 Go + Redis 技术栈一致，避免自研调度引擎的复杂度。
        
    -   自带 Web 监控工具 `asynqmon`，可快速查看队列状态。
        
-   **部署形态**：单个二进制 `cmd/server/main.go` 同时启动 API + Worker，是否启动 Scheduler 通过配置 `ENABLE_SCHEDULER` 控制，便于多实例部署时只让 Leader 跑调度器。
    
-   **前端**：保持 Vue 3 + Vite + Element Plus，作为项目子目录 `web/`。
    
-   **Go func 任务**：通过 `map[string]func(context.Context, map[string]interface{}) error` 注册表实现；前端按名称选择，新函数需在代码中注册后才能在 UI 中使用。

## 4\. 数据模型设计

### 4.1 `jobs` 任务表

```go
type Job struct {
    ID           int64      `gorm:"primaryKey" json:"id"`
    Name         string     `gorm:"size:128;not null;index" json:"name"`
    Type         string     `gorm:"size:32;not null" json:"type"`          // http / shell / gofunc
    Status       int        `gorm:"default:0" json:"status"`               // 0=停用, 1=启用
    ScheduleType string     `gorm:"size:32;not null" json:"schedule_type"` // once / interval / cron
    CronExpr     string     `gorm:"size:128" json:"cron_expr"`
    IntervalSec  int        `json:"interval_sec"`
    ExecuteAt    *time.Time `json:"execute_at"`
    Payload      string     `gorm:"type:text" json:"payload"`              // JSON 配置
    TimeoutSec   int        `gorm:"default:300" json:"timeout_sec"`
    NextRun      *time.Time `json:"next_run"`
    CreatedAt    time.Time  `json:"created_at"`
    UpdatedAt    time.Time  `json:"updated_at"`
}
```

### 4.2 Payload 结构

```go
type HTTPPayload  struct { URL, Method, Body string; Headers map[string]string }
type ShellPayload struct { Command, WorkDir string }
type FuncPayload  struct { FuncName string; Params map[string]interface{} }
```

### 4.3 `job_logs` 执行日志表

```go
type JobLog struct {
    ID          int64      `gorm:"primaryKey" json:"id"`
    JobID       int64      `gorm:"index" json:"job_id"`
    JobName     string     `gorm:"size:128" json:"job_name"`
    TriggerType string     `gorm:"size:32" json:"trigger_type"` // cron / manual
    Status      string     `gorm:"size:32" json:"status"`       // running / success / failed
    Output      string     `gorm:"type:text" json:"output"`
    Error       string     `gorm:"type:text" json:"error"`
    StartedAt   *time.Time `json:"started_at"`
    FinishedAt  *time.Time `json:"finished_at"`
}
```

## 5\. Asynq 任务调度设计

### 5.1 Task Type

-   `job:execute`：统一任务执行类型，payload 中携带 `job_id` 与 `trigger_type`。

### 5.2 一次性任务（At）

创建时通过 Asynq Client 入队：

```go
client.Enqueue(task, asynq.ProcessAt(*job.ExecuteAt))
```

### 5.3 周期任务（interval / cron）

-   interval（5min/10min/30min）：转换为 cron 表达式 `*/5 * * * *`（Asynq 使用 5 位标准 cron，不含秒）。
-   cron：用户输入 5 位标准 cron，后端校验。
-   通过 `asynq.Scheduler.Register(cronSpec, task)` 注册周期任务。
-   任务启用/停用时，从 Scheduler 中注册或注销对应 entry；更新时先注销再重新注册。
    

### 5.4 Worker 执行流程

1.  Worker 从 Redis 取出 `job:execute` 任务。
2.  解析 payload，查询 MySQL 获取最新 Job 配置（防止已修改/删除）。
3.  写入 `job_logs` 记录，状态 `running`。
4.  根据 `Job.Type` 选择 Runner 执行，超时由 `context.WithTimeout` 控制。
5.  更新日志状态为 `success` 或 `failed`，记录 Output/Error。
6.  Asynq 自动处理失败重试（本阶段配置为不重试或最多 3 次，按任务粒度可配）。

## 6. 执行器设计

统一接口：

```go
type Runner interface {
    Run(ctx context.Context, job domain.Job) (output string, err error)
}
```

### 6.1 HTTP Runner

-   使用 `net/http` + `context.WithTimeout`。
-   支持 GET/POST/PUT/DELETE/PATCH。
-   记录 response status、body（截断 64KB）、error。

### 6.2 Shell Runner

-   使用 `exec.CommandContext(ctx, "sh", "-c", command)`。
-   合并 stdout/stderr 作为 output。
-   超时后 kill 进程组。
-   生产环境建议开启命令白名单或关闭 Shell 任务类型。
### 6.3 Func Runner

```go
var registry = make(map[string]func(context.Context, map[string]interface{}) error)

func RegisterFunc(name string, fn func(context.Context, map[string]interface{}) error) {
    registry[name] = fn
}
```

-   按 `FuncName` 查找函数，传入 `Params`。
-   内置示例函数：`helloWorld`、`pingRedis` 等。
-   业务方可注册自定义函数，重新部署后生效。

## 9. 生命周期与启动流程

`cmd/server/main.go`：

```go
func main() {
    cfg := config.Load()
    db := repository.NewMySQL(cfg.MySQL)
    redis := repository.NewRedis(cfg.Redis)

    // 自动建表
    db.AutoMigrate(&domain.Job{}, &domain.JobLog{})

    // 注册内置 Go func
    registry.RegisterBuiltinFuncs()

    // 启动 Asynq Worker（所有实例都跑）
    worker.Start(redis, db)

    // 只有启用调度器的实例才启动 Scheduler
    if cfg.EnableScheduler {
        scheduler.Start(redis, db)
    }

    // 启动 Gin API
    router := handler.NewRouter(db, redis)
    router.Run(cfg.HTTPAddr)
}
```

## 10. 安全与权限

-   **Shell 任务**：建议通过配置 `SHELL_TASK_ENABLED` 控制是否开启，生产环境默认关闭；或加入命令白名单。
-   **HTTP 任务**：可配置 IP/域名黑名单，禁止访问内网敏感地址。
-   **认证鉴权**：本阶段可先不加，后续通过 JWT / OAuth2 / 企业 SSO 扩展。
-   **日志脱敏**：任务输出中若包含敏感信息，需自行在函数/脚本中处理。


## 11. 高可用与扩展

-   **Worker 多实例**：多个实例同时运行 Worker，Asynq 保证一个任务只被一个 Worker 处理。
-   **Scheduler 单实例**：通过 `ENABLE_SCHEDULER=true` 仅在一台实例启用，避免重复调度。
-   **Redis 高可用**：生产环境使用 Redis Sentinel 或 Cluster。
-   **MySQL 高可用**：主从或 RDS。
-   **任务幂等**：任务实现方需自行保证幂等。

Q: Asynq 组件承担着那些工作？

Asynq 在这个方案中承担的是任务队列 + 分布式调度引擎的角色，它本身不执行业务逻辑，而是负责任务的“入队、排队、调度、分发、重试”，真正的 HTTP/Shell/Go func 执行逻辑由我们自己写的 Runner 完成。

具体分工如下：

| 职责                 | Asynq                                | 我们的代码                   |
| ------------------ | ------------------------------------ | ----------------------- |
| 任务元数据持久化           | ❌                                    | MySQL 存储 jobs 表         |
| 执行日志持久化            | ❌                                    | MySQL 存储 job\_logs 表    |
| 一次性任务入队            | ✅ client.Enqueue(task, ProcessAt(t)) | 调用 Asynq Client         |
| 周期任务调度             | ✅ Scheduler.Register(cronSpec, task) | 管理注册/注销生命周期             |
| 任务队列存储             | ✅ Redis                              | ❌                       |
| 多 Worker 消费        | ✅ 自动分发                               | 注册 handler              |
| 失败重试               | ✅ 按配置自动重试                            | 定义重试策略                  |
| 分布式单实例执行           | ✅ 一个任务只被一个 Worker 取走                 | ❌                       |
| HTTP/Shell/Func 执行 | ❌                                    | Runner 实现               |
| 执行结果写入日志           | ❌                                    | Worker handler 写入 MySQL |

Asynq 具体承担的 4 项工作

1.  一次性任务（At 任务）
	前端创建一个“在 2026-07-04 10:00 执行一次”的任务时，后端调用: 	`client.Enqueue(task, asynq.ProcessAt(executeAt))`
	Asynq 会把任务放进 Redis 的延时队列，到指定时间后自动变为可执行，被某个 Worker 取走。
2.  周期任务调度
	前端选择“每 5 分钟执行”或填写 cron 表达式时，后端调用：`scheduler.Register("*/5 * * * *", task)`
	Asynq Scheduler 会按 cron 规则定期把任务推入队列。启用/停用任务时，就是向 Scheduler 注册或注销对应的 entry。
3.  Worker 消费与分发
	所有运行了 server 的实例都会启动 Asynq Worker。Worker 从 Redis 队列中取任务： `mux.HandleFunc("job:execute", handler)`
	Asynq 保证同一个任务只被一个 Worker 实例执行，天然解决多实例部署下的重复执行问题。

4.  失败重试与队列监控
-   任务失败后，Asynq 可按配置自动重试（如最多 3 次）。
-   提供 asynqmon 工具，可以可视化查看队列堆积、失败任务、正在执行的任务等。

一个简单的数据流:

```text
用户创建周期任务
    ↓
Gin API 写入 MySQL (jobs 表)
    ↓
Scheduler 从 MySQL 加载启用任务，注册 cron
    ↓
到点后 Asynq Scheduler 把 task 推入 Redis 队列
    ↓
某个 Worker 从 Redis 取出 task
    ↓
Worker 查询 MySQL 获取最新 Job 配置
    ↓
写入 job_logs (running)
    ↓
Runner 执行 HTTP/Shell/Func
    ↓
更新 job_logs (success/failed)
```

### 为什么选 Asynq 而不是自研 cron？

-   自研 cron 只能做定时触发，任务队列、分布式消费、失败重试、多实例防重都要自己实现。
-   Asynq 把“队列 + 调度 + 消费”都做好了，我们只写业务执行器和 Web 管理界面。
-   与 Go + Redis 栈天然契合，运维成本低。
